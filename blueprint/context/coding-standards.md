# Coding Standards

> Jobmigo conventions: a modular monolith written in TypeScript end to end. One
> TanStack Start app (`web/`) holds the UI and the server code, with PostgreSQL
> through Drizzle.

## Repository Layout

- `web/src/routes`, `web/src/components`, `web/src/lib` - UI, routes and client helpers
- `web/src/server/` - server-only code: database, domain modules, auth helpers (never imported by client components)
- `web/drizzle/` - SQL migrations generated by drizzle-kit
- `prototypes/theme.css` - locked design tokens, ported into `web/` at the first UI feature
- Docker files at the repo root; one `docker compose` setup for local development

## Architecture

- Modular monolith: one deployable app (plus a worker later), split into domain modules under `web/src/server/` (for example `auth`, `profiles`, `jobs`, `evaluation`, `applications`, `ai`, `notifications`, `billing`).
- Each module owns its tables, schemas, service functions and server functions. A module calls another only through that module's service functions, never its tables.
- Routes and server functions stay thin: validate, call a service, return. Business rules live in services.
- No microservices, no extra queue or cache infrastructure until the plan justifies it.
- All model calls go through the AI gateway module. No feature imports a provider SDK directly.

## TypeScript (web)

- Strict mode enabled
- No `any` types - use proper typing or `unknown`
- Server function inputs and outputs are typed once on the server and inferred on the client; no duplicated hand-written copies
- Use type inference where obvious, explicit types where helpful

## React and TanStack Start (web)

- Functional components and hooks only; one job per component
- File-based routes in `web/src/routes/`; route loaders prefetch data through TanStack Query so pages render with data
- Use TanStack Query around server functions for all data (queries, mutations, cache invalidation); no ad-hoc fetch in components
- Server functions and server routes are thin; business logic lives in `web/src/server/` modules
- Client components never import from `web/src/server/`; only server functions and routes do, and secrets stay on the server
- Dynamic routes for item pages (`/jobs/$jobId`)
- Components: `web/src/components/[feature]/ComponentName.tsx`; routes: `web/src/routes/[route].tsx`; helpers: `web/src/lib/`
- Components PascalCase, files match the component or kebab-case, functions camelCase

## Styling (web)

- Tailwind CSS for all styling, Tailwind v4 CSS-first config (`@theme` in `globals.css`)
- Tokens come from `prototypes/theme.css`; no hard-coded colors, radii or fonts in components
- Light theme first; dark mode is not in scope
- No inline styles
- Status and fit are always shown with a text label, never color alone; interactive controls are at least 44px tall
- Every data view has loading, empty and error states

## Server code (TypeScript)

- Strict mode, no `any`; validate every external input at the boundary (Zod arrives with the first public form)
- Errors are `DomainError` subclasses mapped to the stable `{ code, message }` shape; unexpected errors are logged without personal data and returned as `internal_error`
- Server-only modules and files kebab-case or camelCase to match the surrounding code, constants SCREAMING_SNAKE_CASE
- Blocking or long work (file parsing, long AI calls) runs in the worker, not in a request

## Database

- Drizzle ORM with a typed schema in `web/src/server/db/schema.ts`; PostgreSQL only
- Every schema change is a drizzle-kit migration (`npm run db:generate`); never edit the schema by hand or rely on push-style sync
- Review the generated migration before committing; run migrations before the app starts in deployment
- Every user-owned table has `user_id`; use UUID primary keys and `created_at` timestamps
- Shared public data (canonical jobs, companies) has no `user_id`; anything derived from a CV or preferences does

## Data Access and Security

- Scope every user-owned query by the authenticated user id taken from the session, never from client input
- Ownership checks live in one helper (`web/src/server/ownership.ts`), not repeated per route
- Validate all input at the boundary
- Uploaded CVs go to private object storage and are served only through short-lived signed URLs
- Never log CV text, contact details, tokens or API keys
- Secrets come from environment variables by name; never commit them

## AI Gateway

- One interface for all model calls, with the task name selecting model and prompt (cheap vs strong routing lives in config, not call sites)
- Prompts are versioned files; every result records the prompt version
- Every structured output is validated against a schema; on failure retry once, then fail visibly
- Cache by content hash (inputs, prompt version, profile version); reuse before calling a model
- Every call writes a usage event: workflow, model, tokens, cost, cache hit, user
- Generated documents may only use confirmed profile facts; anything else is flagged, never invented
- Fit is a band with per-requirement evidence, never a numeric score

## Background Work

- Jobs are rows in a Postgres job table with a status, attempt count and idempotency key
- Handlers must be safe to run twice; retries use backoff and a max attempt count
- Scheduled work (daily discovery, digest) goes through the same job table

## Error Handling

- Routes raise typed domain errors mapped to HTTP status codes in one handler
- Responses use a consistent error shape; the web app shows user-friendly messages via toast
- Log errors with a request id and no personal data
- External calls (job sources, AI providers, Telegram) have timeouts and retries

## Testing

The blueprint installs no test runner; testing is opt-in at the project level,
because the overlay can't know your stack. Adding unit testing is an explicit
setup task the AI can do through the normal workflow, either as a build-plan item
or with `/tests`. The setup should choose the stack-native runner, wire the
scripts or commands, add a small example test, and update the Commands section
of `AGENTS.md`.

When `AGENTS.md` declares a `Verify` command, treat it as the umbrella automated
gate. It combines only the checks this project actually has, in this order when
available: typecheck, tests, then build. The command does not enable an absent
test runner or replace focused evidence. It gives local work and optional CI one
exact command to run. `/ci` owns Verify and CI setup. `/tests` adds the real test
command to Verify when it already exists, but never creates CI only because
testing was configured.

**The opt-in switch is one signal: a `test` command in the Commands section of
`AGENTS.md`.** Declare one and **tests become a gate for logic-bearing steps**,
not an optional extra; leave it out and the loop verifies logic with the evidence
it already uses (run it, a screenshot, the build). Adding the runner is itself a
deliberate step, never a silent mid-step install. This is the single definition
of the switch; the skills and `ai-interaction.md` only point back here.

- **What to test (the scope rule):** pure logic where a wrong answer is possible -
  parsers, job dedupe and verification, evidence and fit-band rules, credit and cost accounting, permission checks, validators. These have
  assertable inputs and outputs and real edge cases (empty, missing, malformed).
- **What not to test:** UI components and integration-level surfaces (render or
  export routes, anything driving a real browser or external service). Verify those
  with a screenshot and the build, not brittle unit tests.
- **The gate (when a runner is configured):** a build step that adds in-scope logic
  must ship a passing test in the same reviewable diff. The project's test command
  must be green before the step is approved, before any checkpoint commit, and
  before `/complete` merges. UI and integration-only steps are exempt and ride on
  screenshot plus build evidence.
- **When it's named:** the `/feature` spec's Testing section predicts the coverage,
  `/implement` writes the test with the step, and if a step surfaces logic the spec
  didn't foresee, add a focused test then.
- An empty suite should fail, not pass, so "no tests ran" never looks like "passed".
- Run them via the project's test command (see Commands in `AGENTS.md`), not a
  hardcoded tool name.

Stack binding: Vitest runs server tests against a real PostgreSQL test database
(`jobmigo_test`), with external dependencies (AI providers, job sources, Telegram,
storage) faked at the gateway or adapter boundary and time controlled through an
injected clock. Tests live under `web/tests/`.

## Browser Verification

For UI and integration behavior, prefer real browser evidence over reading the
code and assuming it works.

- Browser automation is separately opt-in through `/tests browser`. That setup
  reuses a compatible runner or prefers Playwright for supported projects, then
  documents the exact command as `Browser tests` in `AGENTS.md`.
- When `Browser tests` is declared, add focused coverage for stable behavioral
  done-whens when it is proportionate, and run the documented command during
  `/check`. Do not assume it proves visual fidelity, real authenticated-profile
  behavior, browser chrome, or another claim the test does not observe.
- If no Browser tests command is declared, do not add a runner silently in the
  middle of an unrelated feature. Use the available dev server, browser
  screenshots, build output, API output, or manual evidence instead.
- Browser tests are not part of the default Verify command or CI unless the user
  separately chooses that slower gate.
- Browser evidence is especially important for flows that click, type, submit,
  navigate, download files, render complex layouts, or depend on client-side
  state.

## Code Quality

- No commented-out code unless specified
- No unused imports or variables
- Keep functions under 50 lines when possible

## Comments

Write code that explains itself; comment only what the code cannot say.
Over-commenting is a common AI tell, so resist it.

- Comment the **why**, not the **what**. Delete any comment that restates the code.
- No banner/header blocks, section dividers, or step-by-step narration of obvious
  code. A file does not need a comment announcing each region.
- A comment earns its place only when it captures something the code can't: a
  non-obvious decision, a gotcha or workaround, why a value is what it is, or a
  link to a spec or issue.
- Prefer self-documenting names and small functions over explanatory comments.
- Keep doc comments minimal: a one-line purpose on an exported type or function is
  plenty; don't write JSDoc that just repeats the signature.
- When in doubt, leave the comment out.

## Writing

- No em dashes (U+2014) in generated content: docs, comments, commit messages,
  READMEs, specs. They read as AI-generated.
- Use a hyphen for `term - description` separators; rephrase prose with commas,
  parentheses, or a colon. Avoid en dashes and the ellipsis character too.
